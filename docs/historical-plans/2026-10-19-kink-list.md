# Kink list

## Context

The roadmap's headline Playroom feature: a private record of what someone is
into, curious about and won't do, kept for themselves and shared with
partners.

The groundwork is done (2026-10-19, commit `33311d5`, and `.local/kinks/`).
That covers the roadmap move, a 455-item draft catalogue built from ten public
lists, a categorisation review and a design brainstorm. This plan builds the
feature on top of it, in six phases, each committed on `main` once its tests
pass.

Decided with the user:

- **Answers.** One scale by default: **Hard limit, Not for me, Conditional,
  Don't mind, Curious, Like, Love**. Any kink can also have a detailed answer,
  made of three sliders: interest in the fantasy, interest in actually doing
  it, and experience doing it. There is no fantasy-only toggle; the sliders
  cover it.
- **Notes.** A free-text note can go on any kink, whether or not it has an
  answer.
- **Roles.** Kinks with a role pair (giving and receiving, as dom and as
  sub, …) can be answered for both sides at once, or for each side
  separately.
- **Categories.** One primary category per kink. Each category has an "N
  related kinks" link showing kinks that live elsewhere but fit here too.
  They're editable there: it's the same item, so an answer changed in one
  place changes in both. The categorisation review's changes are applied to
  the catalogue first.
- **Intensity.** Levels 0–6 (Sweet … Extreme). Extreme is hidden until the
  person raises their maximum.
- **Privacy.** Everything a signed-in person writes is sealed. The server
  never learns which kinks were answered.
- **Partners.** A partner list follows your own list except for the answers
  you override for that partner. Answering something there that your own list
  hasn't answered yet writes it to your own list. Hard limits can be
  overridden like any other answer.
- **Search.** Matches names, aliases (synonyms and slang) and custom items.
- **Quick fill.** The four-step flow: triage, swipe deck, drill down, review.
- **No account needed.** Signed out, answers are kept on the device, and a
  link carries them for sharing. People are encouraged to sign up to keep
  their answers and to compare with a partner. Answers on the device join
  the account at sign-in. A signed-in person can compare their own list
  against a shared link.
- **Import and export.** Imports come from the popular lists that let you get
  your answers out. Exports go to a file and a link.
- **Rollout.** On for everyone, with no feature flag.
- **Version history.** A new version is kept once a week passes without
  edits. The point is to look back at how answers changed, not to undo.

## Shape of the code

```
src/lib/kink-list/            alias-free, pure (server- and client-safe)
  catalog.json                the catalogue (generated from .local, then edited by hand)
  catalog.ts                  Zod-validated loader + cross-reference checks, like roadmap/
  share-ids.json              append-only id order for share links and exports
  answers.ts                  levels, Answer type, effective answer and inheritance, merge
  deck.ts                     quick-fill deck: order, drill-down, review buckets
  compare.ts                  role-aware matching, groups, blind mode
  history.ts                  diff between two versions
  share-link.ts               link codec (deflate + base64url, fragment only)
  import/                     detectors and decoders per source, plus list snapshots
src/lib/sealed-kinds/kink-list.ts   kinds 'kink-list' (solo) and 'kink-list-partner'
src/lib/kink-list/store.svelte.ts   the KinkListStore interface: device store and account store
src/lib/components/kink-list/       KinkRow, AnswerScale, DetailSliders, Deck, Triage, …
src/lib/server/kink-lists.ts        every DB access, envelope checks, freeze-on-write
routes:
  (auth-required)/(app)/playroom/kink-list/…   signed in: browse, quick, compare, partner, history, import
  (public)/kink-list/…                         signed out: same UI on the device store; redirects signed-in visitors
  (public)/kink-list/shared                    read-only view of a shared link (#fragment), for anyone
  api/kink-lists/…                             PUT/GET the sealed rows
```

The screens are written once, as components that take a `KinkListStore`
(`answers`, `set(key, answer)`, `triage`, `custom`, `settings`, save status).
The routes are thin wrappers that choose a store. The **account store** seals
into the user's vault and saves through the API. The **device store** keeps
the same payload in `localStorage`. Both validate with the same Zod schema.

## Data

**Sealed payload, kind `kink-list` v1.** Validated by the kind, and merged
per key by the `at` timestamp:

```ts
{
  answers: Record<ItemKey, Answer>;              // ItemKey = catalogue id | `custom:<uuid>`
  triage: Record<CategoryId, { value: 'skip' | 'limit'; at: number }>;
  custom: Record<`custom:${string}`, { name; categoryId; description?; at }>;
  settings: { maxIntensity: 0..6 (default 5); at };
  skipped: Record<ItemKey, number>;              // deck skips, with when
}
Answer = { level?: Level; sides?: { a?: Side; b?: Side }; detail?: Detail; note?: string (≤ 1000); at: number }
Side   = { level?: Level; detail?: Detail }
Detail = { fantasy?: 0..4; doing?: 0..4; experience?: 0..4 }
Level  = 'limit' | 'not-for-me' | 'conditional' | 'dont-mind' | 'curious' | 'like' | 'love'
```

**The effective answer**, worked out in `answers.ts`:

- A side's answer, then the top-level answer.
- Then a specific's parent kink answer, flowing down "kind of" links only.
- Then a category triage of "Hard limit all", which applies only to that
  category's primary kinks.
- Positive answers never flow down from a category, and related kinks never
  inherit anything.

**Tables**, made with `drizzle-kit generate --name …`:

- `kink_lists`:
  - `id`, the client UUID, which the ciphertext is bound to
  - `owner_id` (foreign key, cascade)
  - `scope`: `'self'` or a partnership id
  - `partnership_id` (foreign key, cascade, nullable)
  - `vault_id` (foreign key, cascade)
  - `ciphertext`, `payload_version`, `revision`
  - `edited_at`
  - `timestamps`
  - unique on (`owner_id`, `scope`)
- `kink_list_versions` (phase 6): `id`, `list_id` (foreign key, cascade),
  `vault_id`, `ciphertext`, `payload_version`, `edited_from`, `edited_to`,
  `frozen_at`.

**Server rules** (`server/kink-lists.ts`):

- **Writes** check only the envelope (`sealedIsAcceptable`), and that the
  vault is the right one: the owner's self vault for `'self'`, the
  partnership's vault plus membership for a partner list.
- **Edits** are compare-and-swap on `revision`, as in the Daydreams library
  (`server/daydreams.ts`).
- **On conflict** the client fetches the latest, opens it, merges per key by
  `at`, and saves again.
- **Reads:** you can read your own rows, and your partner's row for a
  partnership you share.

Saves are debounced, with a "Saving… / Saved / Not saved, retry" status. A
`beforeunload` guard stays up while anything is unsaved. Notes keep their
text in the store until the save succeeds. Messaging's drafts helper
(`messaging/drafts.ts`) is reused if it fits, so nothing typed is lost.

## Phase 1: catalogue, your own list, browsing

   Then export to `src/lib/kink-list/catalog.json` and `share-ids.json`.

   cross-reference checks:
   - unique ids
   - parents exist, depth ≤ 3
   - `alsoUnder` names a category

   - intensity 0–6
   - every catalogue id is in `share-ids.json`

   `ALL_SEALED_KINDS`.

   `GET`/`PUT /api/kink-lists/[scope]`.

## Phase 2: quick fill, the four-step flow

At `/playroom/kink-list/quick` (and the public equivalent):

1. **Triage.** A grid of big category tiles, grouped by section.
   - Tapping a tile toggles **Go through / Skip**.
   - Each tile's menu offers **Hard limit everything here**, which is stored
     in `triage` and inherited by that category's primary kinks.
   - The intensity maximum is set here too.
2. **Swipe deck.** One card per kink, showing its name, description,
   intensity and, where it applies, the role pair.
   - Swipe right for Like, up for Love, left for Not for me, down for Hard
     limit.
   - All seven answers are always visible as buttons under the card, so it
     works without gestures. Keys 1–7, the arrow keys, Backspace for undo and
     S for skip also work, and so do screen readers.
   - **Conditional** opens the note field on the card before moving on.
   - After a positive answer to a role-pair kink, chips appear: Giving /
     Receiving / Both.
   - Skip and Undo are always there.
   - The swipe uses pointer events with a threshold. The card's fly-off
     animation is dropped under `prefers-reduced-motion`.
3. **Drill down only after yes.** A positive answer on a kink deals its
   specifics in next, labelled "Specifically: …". A no or Don't mind lets
   them inherit instead.
4. **Review.** At the end:
   - every limit, including inherited ones
   - conditional answers with their notes
   - skipped cards, with "Go through skipped"
   - a link to the whole list
   - signed out, the share link and a sign-up prompt

**How it works underneath:**

- `deck.ts` builds the order: included categories in catalogue order, kinks
  then their specifics, unanswered and within the intensity maximum. Progress
  comes from the answers, so nothing about the deck's position is stored.
- Each answer saves at once.

**Tests:** `deck.ts` unit tests; component tests for the deck's buttons, keys
and undo; e2e for the deck filling a list on a phone-sized viewport (swipe
via pointer events and via buttons).

Commit: `feat(kink-list): quick fill with triage and a swipe deck`.

## Phase 3: no account, sharing, sign-in

1. **The public route** `/kink-list/…`: the same UI on the device store
   (`localStorage` key `kink-list.device`, read through a small `device.ts`
   that treats anything unparsable as absent, like the IQ test's).
   - A signed-in visitor is redirected to `/playroom/kink-list`.
   - A banner says "Saved on this device only", with Sign up / Log in, and
     explains that an account keeps the answers and lets you compare with a
     partner.
2. **The share link** (`share-link.ts`): `/kink-list/shared#k1.<base64url(deflate-raw(JSON))>`.
   - The JSON holds `share-ids.json` indices, levels, sides, details, and
     notes (an "Include notes" checkbox, on by default).
   - The answers live in the fragment, so the server never receives them.
   - Decoding validates against the payload schema, and an unknown index is
     dropped.
   - Version prefix `k1`. `share-ids.json` is append-only, so old links keep
     decoding.
3. **The shared page** is a read-only view of the list from a link.
   - "Make your own" for anyone.
   - **Compare with mine.** Signed in, it goes to
     `/playroom/kink-list/compare#…` against the sealed list. Signed out, it
     compares against the list on the device.
4. **Answers on the device join the account.** After the keyring unlocks in
   the app shell, a device list in `localStorage` is merged into the account
   list per key by `at`, saved, and only then removed. A toast says how many
   answers were added. The app layout checks the key, and the merge module
   loads through `await import()` only when the key exists.
5. **`compare.ts`**, used here for links and in phase 5 for partners:
   - **Role-aware:** my giving matches their receiving, my "as dom" their "as
     sub", my "on me" their "on my partner". Kinks without a role pair match
     directly.
   - **Groups:** You both want this / One keen, one curious / With conditions
     / Worth a talk / Not a match, plus their limits, which are always shown.
     Overlap is shown per category.

**Tests:**

- unit: the share-link round trip, links broken in each way, old indices,
  `compare.ts` cases
- e2e:
  - signed out: fill, share, open the link in a new context, compare
  - sign up, and the device answers appear in the account
  - signed in: compare against a link

Commit: `feat(kink-list): use it without an account, and share a link`.

## Phase 4: import and export

**Export** (`/playroom/kink-list/import`, plus an export menu):

- JSON with full fidelity (the payload plus the catalogue version)
- CSV: category, kink, answer, giving/receiving, the three sliders, note
- the share link

**Import:** paste a link or choose a file, see a preview, then apply. The
preview lists what matched and what didn't. The choice is "Only fill gaps"
(the default) or "Replace my answers", and unmatched items can become custom
items.

**Sources, each with its own decoder in `import/`:**

- **Bound Up:** our share link and our JSON.
- **The Goctionni KinkList family** (MIT): links carry every answer in the
  hash, encoded in base 64 over the list's own positional order. One decoder
  covers:
  - **Goctionni** `v1.0.2`/`v1.0.1`/`v1`, where the link names its version
  - **adhesiveCheese's kinklist**, where the link doesn't name its preset, so
    the user picks Classic, Detailed or Please Don't, defaulting to the one
    whose length fits
  - **KinkSheet** and **notlewdjustkinky** (`kinklist`, `kinklist_irl`)

  Each source has a snapshot of its list (category, item, columns) with the
  catalogue ids it maps to, in `import/lists/*.json`, plus a level map:

  | Their answer | Ours |
  | --- | --- |
  | Favorite | Love |
  | Like | Like |
  | Okay or Indifferent | Don't mind |
  | Interested or Maybe | Curious |
  | No | Not for me |
  | Limit | Hard limit |

  Their columns (Giving/Receiving, Self/Partner) map to our sides by
  position.
- **CSV.** kinkbdsmtest's CSV export is recognised by its headers. Any
  spreadsheet works too, such as the Duchy's list saved as CSV, or your own:
  the first text column is the kink, and an answer column is found by header
  name. Answer words are matched by synonyms (favorite, love, yes, fetish
  need, like, okay, maybe, curious, no, soft limit, hard limit, never), and
  names are matched against our names and aliases.
- **Not supported**, and the page says why:
  - kinkli.st: results live only on its server
  - KNKI: its links aren't documented, and they expire after 24 hours
  - bdsmtest.org: role percentages, not a kink list

**Tests:**

- unit, per decoder, with real links captured from each site as fixtures,
  plus the CSV heuristics
- e2e: import a Goctionni link and a CSV; export JSON and import it back
  unchanged

Commit: `feat(kink-list): import from other kink lists, and export`.

## Phase 5: partner lists and compatibility

1. **Kind `kink-list-partner` v1**, sealed to the partnership vault.
   - It holds `overrides`, `heldBack`, `resolved` (solo plus overrides, minus
     held back), the custom items, `soloRevision`, `blind`, and `at`.
   - Your partner can't open your solo list, so they read `resolved`.
2. **Sharing is explicit.** "Share my list with \<partner\>" creates the row.
   From then on:
   - after every solo save, the account store re-seals `resolved` for each
     partnership it has
   - opening the partner view re-seals if `soloRevision` is behind
3. **Partner view** at `/playroom/kink-list/partner/[partnershipId]`: the
   same browse UI.
   - Each answer is badged "From your own list" or "Just for \<name\>".
   - Editing writes an override. An item your own list hasn't answered is
     written to your own list instead.
   - Per item: "Back to my own answer", "Copy to my own list" and "Don't show
     \<name\> yet".
   - A **Differences** view lists every override.
4. **Compare** at `.../partner/[partnershipId]/compare`.
   - It uses both partners' `resolved` lists with `compare.ts`.
   - **Blind mode:** if either of you has it on, only mutual interest shows,
     along with limits.
   - Tapping a match starts a message thread, through the existing messaging
     `new thread` flow.
5. **A link from the partner page** (`/partner/[id]`) to "Kink lists".

**Tests:**

- server: permissions (member read, owner write, a non-member gets 404)
- unit: re-sealing, override rules
- e2e with two contexts: share, override, the partner sees the effective
  answers, held-back items are hidden, blind mode

Roadmap: `per-partner-kink-list` and `compare-kink-lists` shipped. Commit:
`feat(kink-list): partner lists and comparing them`.

## Phase 6: version history

**Freezing on write**, for the solo list:

- In `updateKinkList`, if `edited_at` is more than 7 days old, one
  `db.batch()` copies the current ciphertext into `kink_list_versions`
  (`edited_from` and `edited_to`) and applies the update. No cron is needed.
- A version opens with `recordId` = the list's id. That's the id it was
  sealed to, and readers upcast old payload versions as usual.

**History view** at `/playroom/kink-list/history`:

- a timeline of versions, plus Now
- pick any two to see **"How you've changed"** (`history.ts`): more into,
  less into, new limits, limits dropped, more experience, notes changed
- each item's detail gains a small history row

**Tests:** freezing on write (with an injected `now`), the `history.ts` diff,
and an e2e test that ages `edited_at` with `sql()`, edits, and sees two
versions.

Roadmap: `kink-list-history` shipped. Commit: `feat(kink-list): version
history`.

## Throughout

- **Conventions:**
  - `resolve()` for every link
  - `tryFetch` for requests
  - `wa-*` components where one fits; a native `<button aria-pressed>` or
    radios where ARIA state matters
  - `--wa-*` tokens only
  - "…" until a sealed record opens
  - no encryption language in copy
  - comments explain *why*
- **Queries** select columns explicitly, and there's an index for every query
  path.
- **Docs and roadmap:** `docs/kink-list.md` stays current every phase.
  AGENTS.md gets a repo-map row for `src/lib/kink-list/`. Roadmap twigs are
  added and shipped for quick fill, sharing without an account, and import.
- **When finished**, copy this plan verbatim to
  `docs/historical-plans/2026-10-19-kink-list.md`.
