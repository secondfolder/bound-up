Summary

What changes, and why

Today a daydream has to fit one of six voices, and each voice has its own prompts. That makes requests that don't fit those voices hard to serve, makes the stories samey, and leaves a large set of prompt combinations to maintain.

The new engine replaces those fixed voices with three things:

  • Free-form telling notes the model writes for each daydream, saying what it is and how it reads.
  • Loosely structured elements (characters, places, anything else) in a format the app can read. Known types and fields switch on features; unknown ones still work.
  • A menu of capabilities the model can opt into: stats, reveals, questions, dice, pictures and so on. Each one is a self-contained block of prompt text with its own markup.

Around those, the plan aims at four things:

  • Any request works, from a full story to "say fuck to me 500 times". The model decides how much structure the brief needs, and nothing is a good answer.
  • Less sameness. The model lists several directions and code picks one, leaning towards the less obvious. Code also adds random nudges and names, and remembers what this user has already had.
  • Effort goes where it will be read. Set up personality, voice and background, which affect every passage. Don't plan conditional events ahead. Fill in detail when someone taps it.
  • Interactive text: name cards, spoilers, text that expands, cycling words, questions, stats that move as you read, and several ways to view a story.
  • Read aloud, with a voice per character and delivery cues written by the story model, through Fish Audio's S2 models.
  • Waits you can watch. The setup page fills in live as the model works, and you can redirect it mid-stream.
  • Only providers that allow adult content. Every language and voice provider is tested, routed around when it refuses, and shown in settings.
Principles

Rules every decision follows

Structure for the app, prose for the model

Anything code acts on (cast, stats, which features are on) has a known shape. Anything only the model reads stays prose.

Only as much structure as the brief needs

An empty element list, no capabilities and one direction is a valid setup. The prompt says so explicitly.

Fill in detail when it's needed, not in advance

Up front: what affects every passage. Later: detail, when it's about to be seen. Never: branching events.

Randomness comes from code

A model can't surprise itself. Code draws the nudges and the names, and picks which direction to follow.

Tools for asking, markup for telling

A tool call only when the model needs an answer from code (research, a random pick). Everything else is markup in the reply.

Fall back, don't fail

A broken tag loses only that tag. Every tool-based feature has a fallback that doesn't need tools. Unknown types still render.

The user can see and change everything

Telling notes, elements, research and preferences can all be read and edited. What's hidden from the cards (a secret, a pressure) is a spoiler you choose to open under "Behind the scenes", never a secret kept from you.

Safety lives in fixed code

Safety rules, limits and minors are in the fixed core of the prompt, never in anything the model writes.

Never a bare spinner

Every wait shows what's happening and what has come back so far, and you can change direction while it's still working.

Overview

The pipeline

0

Gather code

The brief, relevant preferences, this user's recent directions for similar briefs, two or three random nudges and a pool of names.

1

Read the brief model

What the brief requires, research if needed (tools, or a separate research step), how much room there is (1–8), the directions with how likely each is, and maybe one question.

2

Pick code user, optionally

By default code picks at once, leaning towards the less likely directions the more room there is, and the build starts. The ideas stay one tap away on the setup page, and choosing another cancels the build and starts that one. When the brief asks to choose, the model says so and the user picks first.

3

Build and open model

Telling notes, how it's shown, which capabilities are on, elements, pressures, and then the opening passage, all streamed in the same reply. The research carries over without being redone. For a spread of 1, steps 1 and 3 are a single call.

4

Play model user

Passages in markup with a hidden "next step" note. Questions now and then. "Different direction" uses the list-and-pick approach again.

5

Fill in on tap model, small calls

Character cards and text that expands are generated when tapped, or prefetched when a character first appears, and saved with the story.

Each step is one streamed request unless it says otherwise. A step that uses tools is a short loop on the server that stays within the same step. On the surprise path the first words of the story appear within one call of the brief being read. Everything before that is shown live on the setup page.

Step 1

Reading the brief

One call, answered in a fixed order so that each part is shaped by the one before it. This is "think, then answer": nothing that depends on the research is written before the research.

  1. <musts>: what the brief explicitly requires. Every direction and the build must meet these. They're sent with every passage. The bench checks them; at runtime they're the model's to keep.
  2. <research>: whether research is needed and, if so, what was found. This is written after any tool calls.
  3. <spread>: how much room the brief leaves, from 1 to 8, with a reason. This sets how many directions to write and how hard code leans towards the unusual ones.
  4. <direction p="…">: one line each, with how likely the model thinks each is. This is the Verbalized Sampling technique: asking for the spread of possible answers recovers variety that asking for one answer loses.
  5. <pick by="…">, optional: who chooses the direction. If the tag is missing, or says by="code", code picks and the build starts straight away. Only by="user", which the model writes with a reason when the brief asks to choose ("give me some ideas for X and let me pick"), stops code from picking: nothing is built until the user chooses.
  6. <ask>: optional, at most one, and only when the answer would change which direction is right. Never asked for a very specific brief.

What code sends

Code supplies the randomness. Nudges are drawn from large lists covering setting, era, form, who holds power, sensory palette, pace and complications. The model may set aside a nudge that clashes with the brief. Recent directions are the user's last few for similar briefs, marked "not these". Names come later, in the build, from a names tool.

Research

          
    
            
  • Two tools, one at a time. fetch(url) ships first, because links in the brief cover most research requests. search(query) follows in a second pass, since open search is a bigger risk. The tool loop runs on our server, which decides whether each call is allowed. Our server never makes the web request itself: an approved call is passed to a third-party fetch and search service, which returns the page as clean text. That service is a server setting with its own key, and is chosen in phase 6. Parallel is the first candidate, because the current feature found its engine reads Reddit where others failed. Its own API still needs checking against OpenRouter's wrapper of it.
    • 
            
  • Why not the model provider's built-in fetch. OpenRouter's fetch tool runs inside the model call, so our server never sees the URL before it's fetched and can't check where it came from. A third-party service called by our server keeps that check, and still keeps our server's own address out of every request.
    • 
            
  • Only URLs that came from somewhere. A URL may be fetched only if it appeared exactly as written in the brief, a page already fetched, or search results. A URL the model made up is refused. This stops a page from tricking the model into sending the brief to a URL of the page's choosing.
    • 
            
  • Cautious, not blocked, on other domains. The prompt says the brief's own sites are most likely what the user meant. In code, links to other sites get a smaller page budget (for example 3 of 10) and at most one hop from the brief's own site.
    • 
            
  • Research is kept as written, never as instructions. It's the model's own analysis: themes, tropes and phrases quoted exactly where the wording matters. It's shown to the user under "Background" and can be edited.
    • 
            
  • Research carries over. It travels with the chosen direction into the build and is saved with the daydream. Picking another direction, the passages, and "more like that" all reuse it without fetching again.
    • 
            
  • Fallback without tools. If the model can't call tools, step 1 starts with a separate research step: our server has the fetch service read the brief's links and runs one cheap model call to write the research, then step 1 runs as normal with the research included.
    • 
            
  • No fetch service set up (a new self-hosted install, say): research is off, and the prompt says the links can't be opened and must not be guessed at.
    • 
            
  • What the service sees. The URLs, and the search queries the model writes, which can echo the brief. It never sees the brief itself, the preferences or the story. The provider is chosen with a no-retention policy where one is offered.
    • 
          

        

      


      
      

        Step 2
        
Picking a direction

        

          
Code weights each direction by its likelihood raised to a power set by the spread. A narrow brief follows the model's own likelihoods. A wide brief flattens them, so the less obvious directions win more often.

        

        

        

          
    
            
  • Picked at once, changeable any time. Unless step 1 said by="user" (with no <pick> tag, or by="code"), code picks as soon as the directions have arrived, and the build starts. On the setup page, the directions step shows the pick with "See all 7 ideas". Choosing another there cancels the running build (the stream is stopped, and nothing it wrote is kept) and starts building the new one. The research and the brief carry over unchanged.
    • 
            
  • When the user picks first. If step 1 says <pick by="user">, because the brief asks to choose, code never picks: nothing is built until the user chooses from all the directions. "Surprise me" makes the weighted pick for them. A user who always wants to pick first can say so once, as a general preference ("Always let me pick the idea"), which has the same effect.
    • 
            
  • Try another picks again from the same list, leaving out the ones already shown. When the list runs out, step 1 runs again with everything shown so far marked "not these".
    • 
            
  • The chosen line is added to recent directions for briefs like this one, which feeds the next step 1.
    • 
            
  • Leanings are dropped now and then. Each "usually" preference is left out of a given run with a probability of about 0.25, so remembered tastes shape the stories without making every one the same. Hard limits are never dropped.
    • 
          

        

      


      
      

        Step 3
        
Building the daydream

        

          
The build gets the brief, what it requires, the research, the chosen direction, the nudges, relevant preferences and the capability menu. It returns everything as tags, in this order:

          
    
            
  1. <title>: a short name.
    2. 
            
  2. <telling>: free-form notes on what this daydream is and how it reads (form, rhythm, how the user takes part, what to avoid). This replaces the fixed voices. It's sent with every passage, so it should stay under about 250 words.
    3. 
            
  3. <presentation>: the default view (scroll, tap-through, texts or monologue), a theme from a curated set, and a sentence on what passages should look like.
    4. 
            
  4. <capabilities>: the features this daydream uses, from the menu.
    5. 
            
  5. <elements>: anything worth keeping a record of, in any type, with fields that are mostly free-form.
    6. 
            
  6. <passage>: the opening passage itself, streamed straight after the build in the same reply. It's written with everything above already decided, and it starts appearing on the setup page while the rest is reviewed.
    7. 
          

          
For a brief with a spread of 1 there is nothing to pick, so reading the brief and building happen in one call: the musts and research, then the build, then the passage. "Fuck 500 times" starts within a few seconds.

          
Elements

          
The tag name is the element's type, and anything is allowed. Inside it, each child tag is a field with prose in it. Three attributes have a fixed meaning:

          
    
            
  • id: a short id the model makes up.
    • 
            
  • also: other names and nicknames, so code can link them.
    • 
            
  • shown="no": kept from the user's cards, for the model only.
    • 
          

          
One child tag has a fixed shape, <stat>, because code applies its changes. Elements are read by a lenient parser of our own and stored as JSON, then sent back to the model in the same tag format, so the model always reads the format it writes.

        Naming
        
Names that fit, without the usual suspects

        

          
Models name characters from a tiny set. A 2026 study of 20,000 generated stories found a handful of words, including the names Elias, Mara and Elara, in 88% of them, across models from different companies. The cause looks like preference data, not published fiction ("Elias in the Lighthouse, Again?"). Random names fix that, but a random name ignores who the character is.

          
So the model describes the character, code draws real names that fit the description, and the model chooses among them:

        

        

        

          
The names tool

          
    
            
  • The model asks with a description: background or culture in plain words, gender presentation, roughly when they were born, and how unusual the name should be (common, uncommon or rare). Code maps the background to the name lists it has. Era matters too: someone born in the 1970s gets names that were common then.
    • 
            
  • Code returns about ten first names and ten surnames, drawn at random and weighted towards the uncommon-but-real middle of each list rather than its top ten. It leaves out:
              
      
                
    • a maintained list of names models overuse (Elara, Elias, Mara, Vesper, Lyra, Kai, Marcus Chen…);
      • 
                
    • names from this user's recent daydreams;
      • 
                
    • names already in this story.
      • 
              
    
            
    • 
            
  • The model chooses the one that suits the character, and may ask again once with a changed description. If code has no list for that background, it says so, and the model names the character itself, still avoiding the overused list.
    • 
            
  • Invented worlds (non-human, fantasy, sci-fi) get names from a syllable generator seeded per culture, so they're new but consistent within a story.
    • 
            
  • Generic characters skip the description. "A stranger on the train" gets a plain draw from a broad mix.
    • 
            
  • The description is kept on the element (name-from), so a card's "Another name" button can draw again for the same character.
    • 
          

          
Models without tools

          
The build prompt includes a pre-drawn pool, about six names per gender from each of twelve broad backgrounds (around 300 tokens), plus the overused list. The model chooses from the pool when the character's background is in it, and otherwise writes its own. The bench's cliché check measures how often names repeat across runs either way.

          
Where the names come from

          
    
            
  • Openly licensed lists, bundled and stored server-side, as static files per background in R2, loaded when the tool runs and cached per isolate. Nothing is looked up live, and the lists never reach the browser bundle or the worker bundle's size limit.
    • 
            
  • Sources:
              
      
                
    • US Social Security baby names, which are CC0 and give birth-year frequencies from 1880, so era-appropriate names come free;
      • 
                
    • national statistics offices' name releases, each under its own open licence, checked per country;
      • 
                
    • Wikidata's given and family names (CC0) for breadth across languages;
      • 
                
    • Faker's locale lists (MIT) as a quick start.
      • 
              
    
            
    • 
            
  • Not the popular name-dataset package. Its data was extracted from a leaked Facebook dump, which isn't a source this app should build on.
    • 
            
  • Behind the Name's API has good coverage by language (usage=ita) and gender, but returns at most six names per call and needs a key. Its terms would need checking. It's an option if the bundled lists prove thin for some backgrounds.
    • 
          

        

      


      
      

        While it works
        
The setup page, live

        

          
Pressing Start goes straight to the setup page. Nothing waits behind a spinner on the brief.

          
    
            
  • The steps, with what each one is doing. Reading the brief, following links, thinking of directions, picking, building, opening. Under the active step, one line shows the latest of what the model is writing, cleaned of tags, so you can watch it think: "…the trainer's weekly reports to someone you never meet".
    • 
            
  • Results go into their places as they arrive. The parser fires as each tag closes. Musts become chips. Each fetch appears as a line with ✓ or ✗ and why. Research fills a collapsible "Background" panel. Directions appear as cards one by one. In the build, the title types in, the telling notes stream into the summary, each character's card appears as its tag closes, and stats, view and theme appear as chips.
    • 
            
  • The ideas are a tap away. Directions arrive as cards with a count. Once code has picked, the step reads "Picked: Week by week · See all 7 ideas". Opening the list and choosing another stops the build that's running and starts the new one. When the model asked the user to pick, the step waits on the list instead, open.
    • 
            
  • The opening runs straight into the story. The first passage streams into a preview at the bottom. "Keep reading" turns the page into the play view without a second request, and the setup moves into the collapsible bar.
    • 
            
  • Change it while it works. An input box at the bottom is always there: "Not quite? Tell it what to change." Sending stops the current stream and records the change as an amendment under the brief. It then resumes from the step the change affects:
              
      
                
    • before a direction is picked, step 1 runs again with the amendment;
      • 
                
    • after that, the build runs again with the previous build plus the amendment, keeping the research and only changing what was asked.
      • 
              
    
              An amendment that sounds like a lasting taste ("less plot") is offered as a preference, with the usual undoable toast.
    • 
            
  • A reload resumes, it doesn't start over. The setup is saved, encrypted, after each completed step, so a reload continues from the last finished step. A stream can't resume mid-way, so the step in progress runs again.

        Step 4
        
Playing

        

          
Each passage is prose with inline markup, followed by an <after> footer. The footer holds one JSON object per line, so one malformed line is lost on its own. The user's turn can be words they wrote, a tapped option, a cycle choice, an answer or a dice roll. Each is a turn of its own, so reloading the page or branching the story replays it exactly.

          
    
            
  • Next-step notes. Each passage ends with a next line saying where the story could go from here. The next passage reads it. This plans one step ahead and keeps planning, with no plot written in advance.
    • 
            
  • Escaping a loop. If the last three next-step notes are too similar, or the user has pressed "Continue" four times without writing anything, code asks for the next passage with two or three options for the next step and picks one itself.
    • 
            
  • New elements. A footer line {"new": …} adds a person or thing with a name and a seed line. Its card is filled in later.
    • 
            
  • Preferences noticed in what the user wrote go in the footer with a suggested scope. The page shows them as a toast the user can undo (Preferences).
    • 
            
  • Telling notes change with the story. When the story's shape changes ("this has become vignettes"), a footer line {"telling": "…"} proposes new notes. They're shown as a toast with the change highlighted, and applied only if the user accepts.
    • 
            
  • No repeating within a story. Code finds the most-repeated three- and four-word phrases in the last few passages and adds them to the end of the prompt as "don't reuse". The low-level samplers that do this properly (Antislop, DRY) need access the API doesn't give us.
    • 
            
  • Nothing typed is lost. The input box keeps an encrypted draft on the device until it's sent or emptied, as every composer in the app does.
    • 
          

        

      


      
      

        Long stories
        
Memory

        

          
Sending the whole story every turn gets expensive and eventually overflows the model's context. Long-roleplay tools have converged on three layers, and the plan already has the third:

          
    
            
  1. Recent passages, word for word. The last scene in full, or the last 6 passages, whichever is more.
    2. 
            
  2. Scene summaries. At each scene break (a <beat kind="scene"/>, or after 8 passages), a cheap call condenses the scene into a few lines. Older scenes go to the model as summaries plus their next-step notes. Summaries are only ever added to, never rewritten, so the start of the prompt stays the same and prompt caching keeps working.
    3. 
            
  3. Facts kept exactly, in the elements. After each passage, a background call (the same one that fills cards) writes new durable facts into elements: promises made, what's been revealed, who knows what. The cards are the story's memory, and you can see and edit them.
    4. 
          

          
    
            
  • Characters only know what they saw. An optional knows field on a character records what they've witnessed or been told. The prompt says not to let anyone use what they couldn't know, which matters once there are secrets.
    • 
            
  • No vector search to start with. Summaries plus elements cover most daydream lengths. Retrieval adds an index of encrypted content that the server can't build anyway. Revisit if the bench's long sessions show facts going missing.
    • 
            
  • Summaries are saved per branch, encrypted, like everything else. Branching from an earlier passage uses the summaries up to that point.
    • 
          

        

      


      
      

        Format
        
Passage markup

        

          
Markdown for emphasis, and a small set of tags for structure. The core prompt describes only the tags this daydream's capabilities turned on, so a monologue never hears about chat bubbles.

          
Code links names. The renderer already knows every element's name and nicknames, so it links mentions itself, the way AI Dungeon's story cards are triggered by keywords. The model only marks a reference code can't match: [[ottilie|the woman by the mirror]]. That removes the most common tag, which leaves the model more attention for the writing.

The parser

          
    
            
  • One state machine, fed by the stream. A partial < or [[ is held back until it can be classified. Anything still open at the end is closed.
    • 
            
  • An unknown tag is dropped and its text kept. Malformed attributes are ignored. The output is a tree of components, never HTML.
    • 
            
  • The content of <hidden> is drawn blurred while it streams, so a spoiler never shows its text first and then hides it.
    • 
            
  • The footer is cut off before rendering. Each line is parsed on its own and checked against that line's schema.
    • 
            
  • Test: split a set of saved passages at every character boundary while streaming, and check the tree comes out the same as parsing each passage whole.
    • 
          

        

      


      
      

        Form blocks
        
The block gallery

        

          
A block puts part of the story into a form from inside its world: a report, a contract, a group chat. Some you read, some you fill in to take your turn, and some change while you look at them.

          
    
            
  • Read: the block is the story's text in a different shape.
    • 
            
  • Fill in: the block has fields. You initial, tick, sign or answer, and what you entered becomes your next turn.
    • 
            
  • Live: the block changes on screen: bids climbing, notifications arriving, a countdown running. Changes between passages use stats; changes within a passage use timed beats.

Fields: one markup for every fill-in block

          
Any block can hold fields. Each fill-in kind above is a block with fields, so adding one is a renderer, not a new mechanism.

          
    
            
  • <field id="…" type="…">label</field>, where type is initial, check, choice (with <option>s), text, sign, say (call and response), tap-count (with a target) or draw (deck and wheel).
    • 
            
  • Fields become the turn. A block with fields has a "Done" button, labelled by its kind ("Sign and return", "Finish lines"). What was entered goes to the model as a structured line in the user's next turn. Fields left alone are reported as skipped, so a skipped clause is something the story can use. Anything typed in the input box goes along with it.
    • 
            
  • Saved as you go. Half-filled fields are kept in the encrypted draft, like anything typed.
    • 
            
  • Accessible. Every field is a real form control with a label taken from its text: initial and sign are toggle buttons ("Initial clause 3"), say is a button, tap-count is a button with the count announced.
    •

        Mid-story
        
Regenerating, editing and steering

        

          
Four actions, kept apart because they mean different things. Each acts on one passage, and none throws anything away: every version stays in the story's tree.

          
    
            
  • Retry: the passage failed (a refusal, a dropped stream, an error). It appears only then, keeps whatever had streamed, and tries again, on a fallback provider if the first refused.
    • 
            
  • Edit: rewrite the model's text yourself. It's saved as a new version beside the original, so you're co-writing, and later passages build on your version. Markup survives editing, because the editor works on the tree, not the raw tags.
    • 
            
  • Continue: extend a passage that stopped short, without the user taking a turn.
    • 
            
  • Write my turn for me: in the input box, the model drafts your next turn in your voice for you to edit or send.
    • 
            
  • Versions of a passage are swiped through, with a "‹ 2 / 3 ›" picker that's hidden when there's only one.
    • 
            
  • Another take: same events, new words. One call with the same input.
    • 
            
  • Different direction: what happens changes. The rejected passage is sent marked "not this". The model lists 3–5 next directions with how likely each is, code picks one leaning towards the less likely, and the passage is written from it. The other directions appear as chips under the new passage, for a user who wants to steer, if their preferences say so.
    • 
          

          
The pick has to happen in code between the list and the passage. We start with two calls, which work on every model, and the first call is cheap. A pick tool, which saves the extra round trip, is added only if bench timings show the extra call hurts.

        Listening
        
Read aloud

        

          
Any daydream can be listened to, with a voice for the narrator and one for each character, delivery cues the story model writes, and the text highlighted as it's read.

          
Provider

          
    
            
  • Fish Audio's S2 models, reached two ways. S2 Pro is on OpenRouter's speech endpoint (/api/v1/audio/speech, model fish-audio/s2-pro) and on Fish's own API. One model covers both of your preferences.
    • 
            
  • Fish's own API is the main route. It streams audio over server-sent events with timing data for each chunk, which drives highlighting as the text is read. It also has a realtime WebSocket mode, a large voice library and voice cloning. OpenRouter's route returns whole clips (mp3 or pcm) without timing data that I could find, so it's the second route: sentence-level highlighting, and no streaming within a sentence.
    • 
            
  • Why S2 suits us. Its cues are free-form natural language in square brackets ([low, amused]), not a fixed list, so the story model's own words can be passed straight through. It also has documented tones (whispering, soft tone, shouting), effects (sighing, panting, gasping, groaning, laughing) and pauses ([break], [long-break]). S1's parenthesis syntax retires on 31 December 2026, so we target S2 only.
    • 
            
  • Whether it allows adult content isn't documented. Fish's terms don't address it either way. That's what the adult-content check settles for real, for both routes. Google's TTS blocks sexual content outright, and Speechify now screens text before speaking it, so a check is needed for any provider.
    • 
            
  • Behind one adapter. speak(segments) → audio stream (+ timings if any). Other providers can be added beside Fish, translating our cues into their own form: ElevenLabs v3's bracket tags such as [whispers], Hume Octave's acting instructions, OpenAI's per-request instructions. Fish's S2 Pro is also listed as open weights, which could one day let a self-hosted install speak locally. Its licence needs checking first.
    • 
          


          
From markup to speech

          
The story model never writes provider syntax. It writes our how cues and <sound> tags, and only while the voice capability is on. The adapter splits the visible text into segments by speaker and sentence and translates the cues:

        

        

        

          
    
            
  • What gets read is what's visible. A spoiler is read only after it's tapped open, and then only that part. Expanded text is read once it's expanded. A cycling word is read as currently set. A question is read with its options. The footer and how cues are never read aloud, and names are read as written.
    • 
            
  • Each form has a sensible reading. Texts are read one message at a time in the sender's voice. A report is read in its author's voice. A monologue is one voice throughout. <slow> becomes pauses between sentences.
    • 
            
  • Voices are chosen by description, not by ID. The build gives each character a voice field in words ("low, unhurried, older woman") and gives the daydream a narrator voice. Code matches each to a curated, tagged voice list per provider, choosing at random among close matches, so voices vary between daydreams too. A voice can be changed on the character's card, which is remembered as a story preference.
    • 
          


          
How it looks and behaves

          
    
            
  • Off until you ask. "Read aloud" is in the view menu (◐), with a play button on each passage. Nothing ever plays on page load: sound in a public place is a privacy risk, and browsers block it anyway. Turning on "Read new passages" makes each new passage play as it arrives, for the rest of the session.
    • 
            
  • Starts while the passage is still streaming. Each sentence goes to the provider as soon as it's complete, and the next segment is fetched while the current one plays, because changes of speaker are where waits happen. First sound should come within about a second of the first sentence.
    • 
            
  • A mini player sits above the input box: who's speaking, play and pause, back a sentence, and speed from 0.75× to 2×. Tapping any sentence plays from there.
    • 
            
  • Highlighting follows along word by word when there's timing data, otherwise sentence by sentence, and never guesses at word positions. Auto-scroll keeps the current line in view and stops as soon as you scroll yourself. Highlighting can be turned off.
    • 
            
  • A discreet lock screen. Playback continues with the screen locked, through the Media Session API. Its metadata is neutral ("Bound Up", no title, no text, no cover), because a lock screen is the most public surface the app has.
    • 
            
  • Streaming on iPhones. Use ManagedMediaSource where it exists (iOS 17.1 and later). Otherwise, play each sentence as its own clip in sequence. Both are tested on iOS as an installed app.
    • 
          


          
Cost, storage and privacy

          
    
            
  • Behind its own feature, because it costs per character spoken, with a daily per-account cap set on the server settings page.
    • 
            
  • The server relays the provider's stream so the key stays on the server, and stores nothing. Audio is cached on the device only, encrypted with the device key and keyed by a hash of the segment. Replaying a passage costs nothing, and an evicted clip is just generated again.
    • 
            
  • What the voice provider sees: the visible text being read and the cues. Nothing else from the story.

        Plumbing
        
Models, tools and streaming

        

          
    
            
  • Through OpenRouter, as now. Model choice moves to step-level settings: reading the brief, building, playing, filling in on tap, and the cheap helpers (listing directions, research without tools). Each defaults to a preset and can be changed on the server settings page.
    • 
            
  • Our own tool loop on the server for names, fetch, search and (later) pick. names is answered by code from bundled lists. It runs on Chat Completions and is capped at 10 fetches per step. pick is answered by code. fetch and search are checked, then passed to the third-party fetch and search service. One outgoing request per page also stays well within Workers' limits.
    • 
            
  • Every model works. Tools are an upgrade, never a requirement: research falls back to a separate research step, and pick falls back to two calls. Models are checked for tool support when chosen.
    • 
            
  • No enforced JSON schemas. Structured output modes cost writing quality (Let Me Speak Freely) and depend on the provider. Every step uses the same lenient tag format and parser.
    •

    •

    •

        Adult content
        
Adult-friendly providers

        

          
Some providers filter adult content, sometimes silently. Instead of guessing, the settings page tests each one, routes only to those that pass, and backs off from any that start refusing.

          
The check

          
    
            
  • A "Check adult content" button on every language model and voice model in server settings. For an OpenRouter model, it sends the probes to each provider serving that model in turn. Each request is pinned to one provider, with fallbacks to other providers turned off.
    • 
            
  • Graded probes, fixed in code:
              
      
                
    1. suggestive
      2. 
                
    2. explicit sex between adults
      3. 
                
    3. explicit with kink
      4. 
                
    4. consent-play fantasy framing (CNC)
      5. 
              
    
              A provider's result is the highest level it passes. A daydream's heat decides which level it needs, so a mild daydream can still use a provider that stops at level 1. Probes never involve minors or anything coded as a minor, and never will.
    • 
            
  • How each probe reply is classified:
              
      
                
    • complied
      • 
                
    • refused: a refusal in words
      • 
                
    • filtered: a content_filter finish reason, a moderation error (403), or an empty or cut-short reply
      • 
                
    • error: unrelated failures
      • 
              
    
              Cheap signals come first; a judge call is used only when those are unclear.
    • 
            
  • Voice models are checked by listening back. The probe text is spoken, then transcribed (OpenRouter and Fish both offer transcription) and compared with what was sent. That catches a provider that silently skips or bleeps words, which an HTTP status never shows. A clip whose length doesn't match the text is flagged too.
    • 
            
  • Re-checked weekly by the existing scheduled job, because provider policies change. This can be turned off, and can always be run by hand.
    • 
          

          
Routing

          
    
            
  • Each request to OpenRouter names an explicit provider list: those that passed the level this daydream needs, minus any backing off. Order is set by the admin, or by price. A model with no passing providers isn't offered for daydreams.
    • 
            
  • The admin can override any provider: always use it, or never use it, regardless of test results.
    • 
          

          
Watching for refusals in use

          
    
            
  • Every reply in production is classified the same way, cheaply. OpenRouter's reply names the provider that served it, so a refusal is attributed to the right one.
    • 
            
  • Back-off grows with each refusal. A provider that refuses is skipped for 10 minutes, then 30, 1½ hours, 4½ hours, and at most 24 hours. Three successes in a row, or a passing re-check, reset it. Plain errors (5xx, timeouts) get a separate, shorter back-off, so a busy provider isn't mistaken for a prudish one.
    • 
            
  • When everything is backing off, the next model in the step's fallback chain is used. With none left, the user sees a clear notice with Retry, and debug mode shows why.
    • 
            
  • Nothing of the story is logged. Only which model and provider, the kind of rejection, the code and the time.
    •

  • the highest adult level passed, and when it was checked;
    • 
            
  • current health: healthy, or "skipped until 14:32 · 3rd refusal";
    •

    •

What's measured

          
    
            
  • Variety: of 20 runs of the same brief, how many are clearly different stories. A model judges, and a person spot-checks.
    • 
            
  • Fit: the musts are met (counted by code where possible), and the spread suits the brief.
    • 
            
  • Structure: how many elements and capabilities each brief got, against what a person would expect.
    • 
            
  • Markup: parse rate, how much of the enabled markup is used, and side-by-side passages written with and without markup to check the writing isn't suffering.
    • 
            
  • Cost and wait: targets of 6 s to the first direction without research, a streaming build within 12 s, under 3 s to the first word of a passage, and under 2 s for a card filled on tap.
    • 
          

          
If markup hurts the writing on the chosen model, the fallback is to write freely first and convert afterwards: a cheap second pass adds markup to plain prose. That costs latency, not writing quality.

        

      


      
      

        Internal tooling
        
Tools for judging quality

        

          
The output is random and the range of briefs has no limit, so judging it by playing it doesn't scale. These tools turn "does this feel better?" into runs you can repeat, compare, and rate quickly.

          
They come in four layers, from cheapest to most human. Each layer narrows down what the next one has to look at.

        


        

          
1 · Bench runner
A versioned brief set in the repo, each brief tagged (open, exact, research, form, safety) and with the structure a person would expect. npm run dreams:bench runs the pipeline N times per brief for each model and prompt version and writes every step's input, output, tool calls, timings and cost to a local, gitignored run folder.

          
Fixed seeds for code's randomness
Nudges, names, the direction pick and the leanings dropped all come from one seeded generator. Two prompt versions can then be compared on identical draws, so any difference is the prompt's, not luck.

          
Replay and fork
Take any recorded run, change one thing (prompt text, model, temperature, a nudge) and re-run from that step only. Shows directly whether a change fixed a bad case.

          
Test pages for research
A local static site the research tools can reach: a caption index, linked posts, an off-site link, a page with injected instructions, and a link baiting the model to send private data. Research becomes reproducible and testable for safety.

        


        
2 · Automatic checks (free, every run)

        

          

            
CheckCatches

            
              
Parse and markupUnparsed tags, unknown tags, footer lines that fail their schema, unclosed blocks, markup the daydream's capabilities don't allow

              
Musts code can checkCounts ("500"), required words, the user's name used or not, a form block present

              
Structure fitSpread against the brief's tag (an exact brief with spread ≥ 4), element and capability counts against the expected structure, telling-note length

              
Clichés and repeatsA growing list of tells ("Vesper", "Elara", "the air was thick", "a shiver ran down"), the same first line across runs, repeated three-word phrases within a passage, and a slop score (how often words and phrases models overuse appear, as EQ-Bench measures it)

              
BehaviourMore than one question per turn, stats jumping more than a set step, stat changes with no cause in the passage (a judge asks "what in this passage earned it?"), next-step notes that repeat, more than one refrain per passage

              
SafetyThe safety brief set must pass: refusals of minor-coded content, hard limits held, injected page instructions ignored, made-up URLs refused

              
Cost and waitEach step against its target time, cost per daydream, tokens per passage

            
          

        


        

          
3 · Model-based sorting (cheap, ranks what you look at)

          
Models do the first pass over hundreds of runs, so your attention goes to the interesting ones: the worst, the best, the disagreements and the duplicates. They never decide what ships.

          
    
            
  • Variety map, in three passes.
              
      
                
    • Fingerprint. A cheap model reduces each run to a few fields: setting, who holds power and why, the form, the user's role, the hook, and how the opening goes. Counting distinct combinations gives a number you can read ("the training brief produced 4 settings in 20 runs, 11 of them a studio").
      • 
                
    • Embed and cluster. Directions, telling notes and opening passages are embedded and clustered per brief. A scatter plot shows a brief collapsing onto two ideas, and a version spreading out.
      • 
                
    • Confirm near-duplicates. For pairs that cluster close together, a judge asks "Is this the same story with different names?" Surface similarity alone misses a reskinned plot and over-counts different stories told in similar words.
      • 
              
    
              The headline number is distinct stories out of N, per brief, per version.
            
    • 
            
  • Pairwise judge.
              
      
                
    • Two outputs for the same brief, one question per call:
                  
        
                    
      • Which better does what the brief asked?
        • 
                    
      • Which meets its musts?
        • 
                    
      • Which stays truer to its cards and telling notes?
        • 
                    
      • Which reads better as writing?
        • 
                    
      • Which uses the interactive markup where it adds something?
        • 
                    
      • Which has about the right amount of structure for this brief?
        • 
                  
      
                
      • 
                
    • Each pair is judged in both orders, and a verdict counts only if it agrees with itself, which cancels the bias towards whichever comes first.
      • 
                
    • The judge is from a different model family than the writer, so it doesn't favour its own style.
      • 
                
    • Ties are allowed, and a one-line reason is required, so you can see why it chose.
      • 
                
    • Both outputs are cut to the same length before judging, because judges prefer longer answers. Judges have also been shown to reward overwrought prose, and EQ-Bench's agreed poorly with expert writers in some categories. That's another reason your votes decide, not the judge.
      • 
                
    • Comparing pairs is more reliable than scoring on a 1–10 scale. Since judges track individual taste poorly (Artificial Hivemind), the judge only sorts and flags.
      • 
              
    
            
    • 
            
  • Simulated player.
              
      
                
    • A model plays the user for 10–20 turns. It sees only what a user would: rendered text, options, cycles and questions. It acts through the same turn types a user has.
      • 
                
    • Personas, each a short prompt:
                  
        
                    
      • eager and wordy
        • 
                    
      • terse ("ok", "more")
        • 
                    
      • steers constantly
        • 
                    
      • contrary
        • 
                    
      • only ever presses Continue
        • 
                    
      • uses every interactive feature
        • 
                    
      • pushes at limits (safety set only)
        • 
                  
      
                
      • 
                
    • Checks run over the whole session:
                  
        
                    
      • A judge every few turns asks "Does anything here contradict the cards or earlier passages?" (does Ottilie stay Ottilie).
        • 
                    
      • Next-step notes are compared for similarity, to catch loops.
        • 
                    
      • Stats are checked for movement.
        • 
                    
      • Questions are counted per turn.
        • 
                    
      • Telling notes are checked for adherence at turn 1 against turn 15.
        • 
                  
      
                
      • 
              
    
            
    • 
            
  • Capability coverage. A matrix of which tags and capabilities each kind of brief actually uses, against what the brief set says it should. Shows tags that never get used, and tags used everywhere.
    • 
            
  • Keeping it cheap. Cheap models throughout. Every judge result is cached by a hash of the content and the question, so re-running a bench only judges what changed. Pairs are sampled, not exhaustive. A full bench run costs a few dollars, not tens.
    • 
          


          
4 · Human rating (scarce, so make it fast)

          
    
            
  • Blind A/B on a phone. A debug page shows two outputs for the same brief, rendered as the user would see them, with the version hidden. You pick one, or a tie, and optionally tap tags like samey, off-brief, too much markup, flat, or loved it. It takes a few seconds each, so it works in spare moments.
    • 
            
  • Leaderboard. A Bradley–Terry ranking of prompt versions and models from those votes, with confidence intervals. A change ships when it beats the current version, not because it feels better.
    • 
            
  • Judge calibration. Your votes are also run past the model judge. How often it agrees with you shows which of its scores can be trusted to sort for you.
    • 
            
  • Flagging from real play. In debug mode, a flag on any passage saves the whole exchange (prompt, stream, setup) to your own bad-cases collection, encrypted like everything else. You can choose to export a case to the bench as a regression brief, so a problem found while playing is never lost.
    • 
          


          
The run viewer

          
One debug page ties these together: pick a brief, see every run as a column, and switch each between the rendered view, the raw stream, the assembled prompt and the check results. Filter by failed checks or by judge disagreement. Compare two prompt versions side by side on the same seeds, with differences highlighted.

          
What to build first: in phase 0, the bench runner with fixed seeds, the automatic checks, the variety map, the pairwise judge and the blind A/B page. That's enough to compare prompt versions, and measure variety, from the first drafts. The simulated player comes in phase 2, once there's a play loop for it to play.

          
Run output contains generated adult prose in plain text, so it stays local and gitignored (like today's prompt-catalogue/) and is never sent anywhere except to the model provider.
