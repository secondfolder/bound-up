# Vaults: end-to-end encryption for every kind of user data

## Context

Only partner messages are end-to-end encrypted today. Each message is an age
file encrypted to both partners' long-term recipients (`crypto/messages.ts`),
and the encryption code is message-shaped. Anything that gets encrypted has its
own hand-written decrypt `$effect` in each component. History restore pages
through every message and reaction and re-encrypts each one.

The goal is to make that machinery generic and apply it to more user data:
tasks and their completions, rewards and their claims, and message tag names.
Messages move onto the same model, with a real migration for the ones already
stored.

Self-only data (self tasks, self rewards) also has to survive a full lockout.
That needs a partner to help restore it, but **the partner must never be able
to read it on their own, and the account holder must show they are involved**.
The email verification that just shipped provides that proof:
`account_recovery_requests.email_confirmed_at`, set by a link sent to the
account's own inbox.

Decisions already made with the user:
- **Scope:** tasks and completions, rewards and claims, tag names, messages, and
  partnership names and roles. The account's own `user.name`, which Better
  Auth holds and admin search uses, stays plaintext.
- **Invites carry a key in the URL fragment.** The names on an invite are
  sealed under it. Link previews and the invite page's title no longer show
  the inviter's name, which is accepted.
- **Push notifications say no names.** "New message" and "New reaction", never
  "from {name}".
- **Shape:** one sealed payload per record, not one ciphertext per field.
- **Keys:** per-scope "vault keys", including for messages, with a migration of
  existing data.
- **Self-data recovery:** a 2-of-2 escrow between the partner and the server. The
  server's half is released only after the emailed link is followed.
- **No sync framework.** Jazz was evaluated and rejected. Jazz v2 trusts its
  server for permissions and has no full end-to-end encryption. Classic Jazz
  is in maintenance mode, and its maintainers are moving users to v2. Neither
  targets D1.
- **Envelope plus sealed body.** Drizzle and SQL migrations keep managing the
  plaintext envelope: ids, scope, foreign keys, the fields the server acts on,
  `payload_version` and `revision`. The sealed body is versioned, validated and
  migrated in application code.

## Design

### Vaults

A **vault** is one random 256-bit symmetric key per scope:
- **Self vault:** one per user.
- **Partnership vault:** one per partnership.

Records are encrypted with AES-256-GCM under the vault key, through WebCrypto
with a non-extractable key. The vault key is wrapped, age-encrypted, to the
recipient of each member who may open it.

**Why symmetric rather than age to a vault public key.** Anyone can encrypt to
a public key, including the server. With a public key, the server could write
a convincing forged task or message. With a symmetric key, only someone who
holds it can produce a record that opens, so the server cannot forge content.
A partner still can, and partners are trusted. A symmetric key is also cheaper
per record, and works as a non-extractable `CryptoKey` on every browser. Restoring
access after a key change then means re-wrapping one key, not re-encrypting
every record. This is the same per-file-key indirection attachments already use
(see `MessagePayload` in `crypto/messages.ts`).

New tables in `schema/app.ts`:

| Table | Columns | Notes |
| --- | --- | --- |
| `vaults` | `id`, `kind` (`self` \| `partnership`), `owner_user_id` (nullable), `partnership_id` (nullable), `key_check`, timestamps | Unique on `owner_user_id` and on `partnership_id`. A check constraint makes exactly one of the two set. Cascades from user/partnership. `key_check` is a public fingerprint of the key: HKDF of the key with info `bound-up-vault-check-v1`. It is pinned, compared, and used in the safety number. |
| `vault_wraps` | `id`, `vault_id`, `user_id`, `ciphertext` (the vault secret age-encrypted to the member's recipient), `for_recipient`, timestamps | Unique on (`vault_id`, `user_id`). `for_recipient` lets a device tell that a wrap is for an old key. |
| `vault_escrows` | `id`, `vault_id` (self vaults only), `partnership_id`, `ciphertext`, timestamps | One per partner. See [Escrow](#escrow). |
| `vault_escrow_relays` | `id`, `escrow_id`, `recovery_request_id`, `ciphertext`, timestamps | Written by the helping partner during recovery. |

**Vaults are created lazily, on one path only.**
- When the keyring unlocks, `ensureVaults()` creates the self vault if it is
  missing.
- It also creates a partnership vault for each active partnership that has
  none, wrapped to both members.
- This one path covers new accounts, new partnerships and every existing one,
  so there is no separate migration step for vaults themselves.
- If two devices race to create the same vault, the server's unique index
  decides. The loser gets 409, fetches the winner's vault and uses that.

**Opening vaults.**
- After the identity unlocks, the keyring fetches the user's wraps
  (`GET /api/vaults`) and opens each one.
- It checks that the opened key's fingerprint equals `vault.key_check`, so a wrap
  for some other vault cannot be passed off as this one.
- The wrap's plaintext also names the vault id it belongs to.
- Opened vault keys are imported as non-extractable AES-GCM `CryptoKey`s and
  held in memory.
- Index keys are derived from the vault key with HKDF and held the same way.
  See [Constraints](#constraints-the-database-still-enforces).
- They are never persisted. They are a few kilobytes, fetched once per load.
- `Keyring.unlocked` gains a `vaults` map.

**Trust.**
- The partner's wrap is made by our own device, encrypting to the partner's
  recipient. That recipient goes through the existing pin and trust check
  (`pins.ts`, `trust.svelte.ts`), so a substituted partner key blocks vault
  creation just as it blocks sending today.
- The partnership vault's `key_check` is pinned per device too, using the same
  pin store with a `vault:<partnershipId>` pin id. A change in it is
  reported like a changed partner key.
- The safety number becomes v2: `SHA-256("bound-up-safety-v2\n" + sorted user
  recipients + partnership vault key_check)`. Comparing it then also detects a
  vault that a dishonest server created and wrapped to both members' public
  keys.
- **Every write that seals to a partnership vault checks
  `trustAllowsSending`.** Reactions and embed-metadata writes currently skip
  this check (`ThreadView.svelte:195,233-260`). The generic `seal` call takes
  the trust state, so a missed check fails the type check instead of being
  silently skipped.

### Sealed records (the generic layer)

**`src/lib/sealed.ts`** is pure and alias-free, so the server and the Drizzle
schema can import it. It holds:
- `RecordKind`: `message`, `messageMetadata`, `reaction`, `task`, `taskCompletion`,
  `reward`, `rewardClaim`, `tag`.
- Each kind's payload type and its Zod schema.
- Each kind's ciphertext size cap.
- The shared `ciphertextSchema`, moved from `schemas/messageForm.ts`.

**`src/lib/crypto/sealed.ts`** is browser-only:
- `seal(kind, recordId, payload, vault, trust)` and
  `open(kind, recordId, ciphertext, vault, payloadVersion) → payload | null`.
- **Ciphertext format:** `sb1.` prefix, then base64 of
  `12-byte IV ‖ AES-256-GCM(JSON payload) ‖ tag`. The prefix lets a later
  change of algorithm tell old blobs apart without guessing, as Bitwarden's
  EncString and Standard Notes' protocol versions do.
- **AAD:** `"bound-up-sealed-v1|" + kind + "|" + recordId + "|" + vaultId + "|" +
  payloadVersion`.
  - A ciphertext moved to another row, another kind or another vault fails its
    tag check.
  - So does one whose plaintext `payload_version` was edited. That stops the
    server downgrading a record to an older reading.
  - This replaces the earlier idea of embedding the context in the plaintext.
- **After decrypting,** `open` runs the payload through the kind's version
  registry: validate against that version's schema, then upcast to the latest.
  - Rich-text descriptions go through the existing `richTextFieldSchema` logic,
    which used to run on the server.
  - The server can no longer sanitise, so the reader does. Whatever comes out
    of a vault is untrusted input.

### Payload versions and migrations

Each kind has a registry in `src/lib/sealed.ts`:
`[{ version, schema, upcast? }]`, a hand-rolled list on Zod.

Libraries were considered and turned down:
- verzod: Zod-only, maintenance unclear.
- doba: a Standard Schema registry, maturity unstated.
- Effect Schema: brings in the whole Effect ecosystem.

The registry is about 100 lines, and the crypto binding and fixtures belong
beside it anyway.

**Rules,** borrowed from event-sourcing upcasting:
- Writers always write the latest version.
- Readers accept every version ever shipped, and upcast step by step.
- Changes are additive by default: new fields get defaults, old fields stay
  readable.
- Renames, splits and changes of meaning go in an upcaster.
- **Readers ship before writers.** A new version's reader goes out in one
  release, and the writer that produces it in a later one. A tab still open on
  the old build then never meets data it cannot read.

**Lazy write-back.** A device that opens a record at an old version re-seals it
at the latest and writes it back.
- The write is compare-and-swap on `revision`: update only where the revision
  is still the one that was read.
- A background migration therefore never overwrites a newer edit from the
  other partner.
- Every sealed write bumps `revision`. A real edit that loses the race reloads
  and is shown the newer content. It is never silently dropped.

**Knowing when an upcaster can go.** `payload_version` is plaintext, so the
server can count rows still on each version. When a version's count reaches
zero, its upcaster and schema can be deleted. The count is recorded in
`docs/temporary-code.md` whenever one is outstanding.

**Frozen fixtures.** Every version ever shipped has a sealed fixture under a
fixed test key. CI opens and upcasts each one, the same way `kdf.test.ts`
freezes the KDF. An old format can then never stop reading silently.

### Constraints the database still enforces

- **Relationships, ownership, counts, enums** stay plaintext columns with real
  constraints and foreign keys.
- **Uniqueness uses blind indexes.** For example, a tag name gets a plaintext
  `name_index` column holding
  `HMAC-SHA256(indexKey, normalise(name))`, at full length.
  - `indexKey` is HKDF of the vault key, with info
    `bound-up-index-v1|<kind>|<field>`.
  - The unique index on (`partnership_id`, `name_index`) stays.
  - The server learns only that two tags in one partnership share a name.
  - Full length, because a truncated index can collide and refuse two
    different names.
- **Sorting, filtering and search** happen in the browser after decrypting.
  The volumes per scope are small.

**Record ids are chosen by the client** (`crypto.randomUUID()`), because the
id is part of the AAD. The server checks the id is a UUID and not already
taken.

**`src/lib/sealed-cache.svelte.ts`** replaces the hand-written decrypt
`$effect`s (`ThreadView.svelte:77-138`, `ThreadSticker.svelte`):
- A small reactive class, cached by `kind:id:ciphertext-hash`, written the
  Svelte way rather than as a port of something else.
- `opened(kind, id, ciphertext, vaultId)` returns `undefined` while working,
  `null` when the record cannot be opened, and the payload otherwise. These are
  the same three states `MessageBubble.svelte` already renders.
- It does nothing until the keyring is `unlocked`, which keeps the
  "placeholder, never content" rule.

**Server: `src/lib/server/vaults.ts`.**
- Membership checks, vault, wrap and escrow CRUD, and `vaultIdFor(scope)`.
- A sealed write stores `ciphertext`, `vault_id`, `payload_version` and
  `revision`, and checks:
  - the vault belongs to the record's scope (self → owner, partnership → that
    partnership);
  - the size cap;
  - the UUID;
  - that `payload_version` is one the server knows;
  - the expected `revision` (compare-and-swap).
- Routes: `src/routes/api/vaults/…`.

**Forms.** Task and reward forms stay superforms + Zod server actions. They
follow the `authSecret` pattern from the login form:
- the plaintext inputs have no `name`;
- `onSubmit` seals and fills hidden `id` and `ciphertext` fields;
- Zod validates the shape (title 1–80 characters, completion messages ≤ 20,
  description ≤ 500 visible characters) **in the browser** before sealing.

The server can only check sizes and counts. The same reasoning applies as for
password strength in `docs/encryption.md`: a policy that has structurally moved
into the browser. Permissions such as `control` and authorship stay on the
server, as invariant 14 requires.

### What each kind seals

| Kind | Scope | Sealed payload | Stays plaintext (server needs it) |
| --- | --- | --- | --- |
| self task | self | title, description, completionMessages | `completion_message_count`, schedule, active, credits, timestamps |
| partnership task | partnership | same | same, plus createdBy and timezone owner |
| task completion | task's scope | snapshot of the task's payload | `completion_message_index` (the server's random pick from the count), credits |
| self / partnership reward | its scope | title, description | cost, active, createdBy |
| reward claim | reward's scope | snapshot of the reward's payload | cost, claimedBy |
| message tag | partnership | name | color |
| message / metadata / reaction | partnership | unchanged payloads | everything already plaintext |

Notes:
- **Completion message.** `chooseCompletionMessage()` (`server/tasks.ts:349`)
  now picks an *index* in `[0, count)`. The completion row stores that index,
  and the reader shows `snapshot.completionMessages[index]`.
- **Snapshots** copy the task's or reward's `ciphertext` as-is. They are sealed
  to the scope's vault, so the partner who completes or claims can trigger the
  copy and both partners can still read it.
- **Tags.** Uniqueness moves from (partnership, name) to (partnership,
  `name_index`), the blind index. Duplicate checks compare `name_index`.
  Sorting by name (`server/messaging.ts:941`) moves to the browser.
- **Widgets** (`toTasksWidgetView`, rewards widgets) return ciphertext and the
  vault id instead of titles. Cards decrypt on the client. Titles are already
  kept out of SSR per `docs/section-widgets.md`.

### Escrow

Escrow lets self-only data be restored after a full lockout, and needs both the
partner and the account holder's own inbox.

**Making an escrow, per partner,** on the owner's device:
1. The server derives a share `S = HMAC(BETTER_AUTH_SECRET, "vault-escrow|" +
   escrowId)`. It is never stored, so a stolen database alone does not contain
   it. `POST /api/vaults/self/escrows` returns `S` to the owner, who is signed
   in and already holds the vault.
2. The owner computes `inner = AES-256-GCM_S(selfVaultKey)`, with
   AAD = `"bound-up-escrow-v1|" + vault.id + "|" + vault.key_check`.
3. The owner computes `ciphertext = age-encrypt(inner, partnerRecipient)` and
   stores it.

What each party can do:
- The partner can open the outer layer, but only gets `inner`.
- The server holds `ciphertext` and `S`, but cannot open the partner's layer.
- Opening it needs both a partner and the server.

`ensureVaults()` keeps one escrow per active partnership. A user with no partner
has no escrow, so a full lockout loses their self data. This is documented, and
the partner-invite flow says so.

**Recovery** follows the existing flow in `docs/account-recovery.md`:
1. **The helping partner** (`RestoreRequests.svelte` → a new
   `runVaultRestore`) compares the code as now, then:
   - adds a partnership-vault wrap for `request.requestedRecipient`;
   - opens the requester's self-vault escrow with their own identity and
     re-encrypts `inner` to `requestedRecipient` as a
     `vault_escrow_relays` row.

   The final step approves, as the last restore page does today. Partner
   approval and the confirmed email are still both required to complete.
2. **Completion** (`/api/account-recovery/complete`) deletes the account's old
   `vault_wraps`. They are for a recipient that no longer exists.
3. **The requester's first unlock** finds a relay for their self vault and
   calls `POST /api/vaults/self/escrow-release`. The server returns `S` only
   if:
   - a recovery request for this user is `completed`;
   - its `email_confirmed_at` is set;
   - it was approved by the partner whose escrow the relay came from;
   - it completed within the last 7 days.

   The device then decrypts the relay with its new identity, then `inner` with
   `S`. It checks the result matches `vault.key_check`, writes a fresh self
   wrap and deletes the relay.

   Every escrow is then **replaced** with new ids, and so new `S` values,
   because `S` has now been released.
4. **Collusion.** A server and partner working together can open the self
   vault. This is inherent to 2-of-2 escrow and is stated plainly in the docs.

### Migration (existing data)

The server cannot encrypt or re-encrypt, so all migration runs on members'
devices, in the background once the keyring has unlocked. It reuses one
generic `migrateScope(scope)` loop that pages through rows, seals them and
posts them back.

**Messages.**
- `messages`, `message_reactions` and the metadata sidecar gain
  `vault_id` (nullable), `payload_version` and `revision`.
- A null `vault_id` means the old two-recipient scheme. Readers try the
  partnership vault if `vault_id` is set and the user identity otherwise.
- Either member's device re-encrypts old-scheme rows to the vault. This needs
  `PUT /api/partnerships/[id]/sealed-migration`, a server-checked endpoint that
  only accepts rows in that partnership which have no `vault_id` yet.
- This reuses the paging in `listHistoryForRestore` and `applyHistoryRestore`
  (`server/messaging.ts:1469,1610`), generalised.
- Every migration write-back is compare-and-swap on `revision`, like the lazy
  version write-back.

**Tasks, rewards, completions, claims, tags.**
- The plaintext columns become nullable. `ciphertext`, `vault_id`,
  `payload_version` and `revision` are added, and so is `name_index` on tags.
- Allowed migrators:
  - the owner, for self rows;
  - either member, for partnership rows.

  They seal unsealed rows, and the server **nulls the plaintext columns in the
  same batch**.
- Reads prefer ciphertext.
- Every write path writes ciphertext only, from the moment this ships.

**What stays temporary.**
- The old message scheme and the nullable plaintext columns stay until every
  row is sealed.
- Accounts that never sign in again would keep them forever. A later change
  decides when to drop the columns.
- This is recorded in `docs/temporary-code.md` with the query that counts
  unsealed rows.
- Drafts stay sealed to the user's own identity on the device. They never
  reach the server, and losing them on full recovery is acceptable.

**DB migrations** come from `drizzle-kit generate --name …`, one per phase, and
each generated SQL file is read before it is committed.

### Partnership names and roles

The four fields — `inviter_name`, `invitee_name`, `inviter_role` and
`invitee_role` — become one sealed record per partnership, kind `partnership`:
`{ inviterName, inviteeName, inviterRole, inviteeRole }`.

Plaintext that stays on the row: `status`, `control`, `inviter_id` /
`invitee_id`, the invite token's hash, expiry and timestamps.

**Creating an invite** (inviter's device):
1. Generate a random 256-bit **invite key** `K_inv`.
2. Seal the invite payload under `K_inv` with AES-GCM and
   AAD = `"bound-up-invite-v1|" + partnershipId`. The payload is:
   - the four name and role fields;
   - **the inviter's own recipient.**
3. Store that ciphertext on the partnership row. Also store `K_inv` wrapped to
   the inviter's own recipient, so the inviter's other devices can show,
   edit and re-share the pending invite.
4. The link is `/invite/<token>#k=<base64url K_inv>`. The fragment never
   reaches the server, its logs or a link preview.

**Accepting** (invitee's device):
1. The page reads `K_inv` from the fragment and opens the invite payload.
   Everything stays a placeholder until then, so names appear only after
   hydration.
   - A missing or wrong key shows "This link is incomplete — ask for it to be
     sent again", never someone else's data.
2. **The inviter's key arrives out of band.** The recipient inside the payload
   is authenticated under a key the server never had. The invitee's device
   compares it with what the server serves and pins it as **verified**.
   - A mismatch blocks accepting, with the same wording as a changed key.
   - This removes trust-on-first-use for that direction. It is the follow-up
     `docs/encryption.md` lists as not built.
3. The invitee's device creates the partnership vault at once, wrapped to both
   members. It seals the partnership record, as the invitee edited it, into
   the vault.
   - It posts the vault, both wraps and the sealed record with the accept.
   - The server deletes the invite ciphertext and the wrapped `K_inv` in the
     same batch.
   - `ensureVaults()` still covers partnerships accepted before this ships.
4. **Permissions stay on the server** (invariant 14). `acceptInvite` still
   decides from the stored row whether the invitee may set names, and
   `control` still gates later edits. What the server can no longer do is
   tell what changed, so who may write the record is the rule. Later edits
   are compare-and-swap on `revision`.

**Rotating the token** (`rotateInviteToken`) generates a new `K_inv` and
reseals the invite. The old link stops working on both halves.

**Invariant 12 moves to the browser.** `viewPartnership()` still owns the
"theirs vs. mine" mapping, now over the decrypted record. The server never
reads names at all.

**Where the name used to be drawn without a key:**
- The invite page `<title>` and its OG/share title become generic: "You've been
  invited to Bound Up".
- Server-rendered titles on the messages pages, the widgets' context line and
  reward balance labels show a placeholder until hydrated, like task titles.
- Push notifications: `buildPushContent` drops the name, giving
  "New message" and "New reaction". The service worker never needs a key.
  `docs/notifications.md` already forbids content in a notification; this
  extends that rule to who it is from.

**Migration:** existing partnerships are sealed by either member's device, like
tags. Pending invites made before this ship have no `K_inv`. They stay
plaintext until accepted or rotated, and the invite list offers to re-share
them, which rotates them.

### Keep in mind: collaborative rich-text pages (not built here)

Notebook pages may later be edited by both partners at once, as rich text. The
likely shape:
- Lexical's own Yjs binding, `@lexical/yjs`, which has no React dependency.
- Updates encrypted and signed under the partnership vault key.
- A Durable Object that only orders and stores ciphertext.
- Clients that write sealed snapshots for readers and for compaction.

Nothing here builds that. These choices keep it open:
- **A symmetric vault key per partnership.** Yjs updates and cursor messages
  can be encrypted under it, with the page id and sequence number as AAD. No
  second key scheme is needed.
- **The sealed record layer is not tied to D1 rows.** `seal` and `open` take a
  kind, an id and a version, not a table. An encrypted Yjs update, or a page
  snapshot, can be one more `RecordKind` later.
- **Versioning covers the rich-text shape.** Under Yjs the editor's own node
  tree would be persisted. So a rich-text payload carries a document-format
  version, and changes to editor-only nodes are treated as format changes.
- **No assumption that the server merges.** Concurrency is compare-and-swap on
  `revision` for records. Merging, if it ever comes, happens on the client.

## Phases (each one shippable and green on the full loop)

1. **Vault foundation.**
   - Tables, `server/vaults.ts`, `/api/vaults`, `crypto/vault.ts`.
   - Keyring vaults, `ensureVaults()`, vault pins, safety number v2.
   - `sealed.ts` with the version registry, `crypto/sealed.ts` with AEAD, the
     `sb1.` format and AAD.
   - Blind-index derivation, compare-and-swap write-back,
     `sealed-cache.svelte.ts`.
   - No data uses vaults yet.
2. **Messages on partnership vaults.**
   - New messages, reactions and metadata seal to the vault.
   - Background migration of old rows.
   - Trust check on every write.
   - Restore becomes "wrap the vault, plus migrate any old-scheme rows still
     left".
   - `ThreadView` and `ThreadSticker` move to `sealed-cache`.
3. **Escrow and recovery.** Escrows, relays, the release endpoint, and the
   changes to `RestoreRequests`, completion and first unlock.
4. **Tasks and rewards.**
   - Sealed forms and server actions.
   - Index-based completion messages, ciphertext snapshots, widgets.
   - Migration of existing rows.
5. **Tags.** Move uniqueness to the blind index, sort on the client, migrate.
6. **Partnership names and invites.**
   - Invite keys in the fragment, the out-of-band inviter key, and creating the
     vault at accept.
   - The sealed partnership record, and `viewPartnership()` over decrypted
     values.
   - Generic push text and generic invite titles.
   - Migration of existing partnerships.
7. **Done-ness.**
   - Docs and roadmap.
   - Copy this plan to `docs/historical-plans/2026-10-16-vaults.md`.

    latest schema.
  - Blind-index vectors, including normalisation.
- **Crypto** (node):
  - Seal/open round trip.
  - `open` rejects a swapped `recordId`, `kind` or `vaultId`, or an edited
    `payload_version`.
  - A record sealed with a key the server could hold, such as one derived from
    public data, does not open.
  - A wrap for the wrong vault is rejected.
  - Escrow: the partner alone cannot open, the server share alone cannot open,
    both can.
- **Server** (in-memory DB):
  - Vault creation race returns 409.
  - Wraps only for members.
  - Sealed writes refuse a vault from another scope.
  - Migration endpoints accept only unsealed rows in scope, and null the
    plaintext.
  - Escrow release refused without `email_confirmed_at`, without approval, by
    the wrong partner, after 7 days, or twice.
  - Completion stores an index within the count.
  - Tags with the same name conflict through `name_index`.
  - The invite page's load and the push payload contain no name.
  - Accept refuses to set names the stored row does not allow (invariant 14),
    and deletes the invite ciphertext and the wrapped `K_inv`.
  - Compare-and-swap: a write-back at a stale `revision` is refused, and the
    newer edit survives.
- **Component** (browser): the `sealed-cache` three states, and the
  placeholder while not unlocked.
- **E2E:**
  - Two partners exchange messages, tasks, rewards and tags. The database holds
    no plaintext: assert via `sql()` that the old columns are null and the
    titles are not in the row.
  - An old-scheme message gets migrated and still reads.
  - Full lockout: the requester gets back partnership data and self tasks only
    after both partner approval and the email link. With approval alone, self
    data stays unreadable.
  - A changed vault recipient warns and blocks sending.
  - Invite round trip: the link carries `#k=`, and the invitee sees the
    inviter's names only after hydration. The inviter's key is pinned as
    verified.
  - A link with the fragment stripped shows "incomplete", not data.
  - A served inviter key that differs from the one in the fragment blocks
    accepting.
